A report API and a report worker need to agree on what work means. They do not
need to share an HTTP server, a renderer or provider credentials.

| Part          | Report example                                  | Responsibility                                                  |
| ------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| Queue         | `reports`                                       | A logical lane from which a worker claims jobs.                 |
| Definition    | `reports.send`, version 1                       | Queue-independent name, version and payload Schema.             |
| Payload       | A synthetic report ID                           | Validated handler input. Prefer references to private data.     |
| Producer slot | `send` on `reports.request`                     | Binds a business consequence to a definition, route and policy. |
| Handler       | Load inputs, render and store the report        | Application work installed with `JobGroup.handlers`.            |
| Worker        | Storage, job API, installed handlers and queues | Executes claims under durable ownership with per-queue limits.  |

In application setup, bind the definition to a queue on the producer slot:

```ts
const reportSetup = Effect.gen(function* () {
  const ReportsQueue = yield* JobQueue.make("reports")
  const SendReport = yield* Job.make({
    name: "reports.send",
    payload: Schema.Struct({ reportId: Schema.String })
  })
  return yield* JobProducer.make("reports.request").pipe(
    JobProducer.withSlot("send", SendReport, { queue: ReportsQueue })
  )
})
```

Even a producer with just one slot needs `JobProducer`: the job definition says what work means; the producer says which business operation can enqueue it and supplies its route and policy. The worker doesn't need that producer definition to run the job.

## Which contract runs and which write deduplicates?

A stored **`JobAddress`** is `(queue, name, version)`. The worker claims from the
queue and dispatches by name and version. `Job.make` defaults the version to
`1`. An incompatible payload change needs a new version and a matching decoder.

The **deduplication key** is `(operation, operationId, slot)` in the configured
storage. Reuse the operation ID and slot on request retries. When evidence
is retained, matching name, version, payload format and semantic payload return
the original job ID. A difference in those fields conflicts. The first queue,
policy and initial availability remain in effect.

Two slots may enqueue the same name. Two slots do not create ordering or a flow.
Use separate consequences for generation and delivery, with an explicit
application-owned handoff. See [deduplication](/docs/persistence/deduplication).

## Layers make execution explicit

The application supplies `JobStorage` and installs handlers with
`JobGroup.handlers` for every group in the worker's `JobApi`. It then constructs
the worker and explicitly runs a finite drain or scoped polling runtime.

The `concurrency` option limits concurrent claims and executions for a queue
within one worker instance. Each replica has its own limit. See
[workers](/docs/execution/workers) for lifetime and shutdown, or
[Getting Started](/docs#your-first-job) for a concrete composition.
