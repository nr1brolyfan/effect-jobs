The API makes business identity, transaction ownership and uncertain outcomes explicit.
That adds a little setup; it avoids guessing what a failed request actually did.
Durable state belongs to storage, not a long-lived process: the same execution
model supports permanent workers and bounded, short-lived invocations.

:::note[API version]
This page uses `Job.make`, slot-bound `JobProducer` declarations and the
`JobRegistry` handler installation contract.
:::

## Contracts, handlers and slots

### Why separate the contract from its handler?

The API server needs to know what a job means, not how the worker sends email.
`Job.make` declares `name`, `queue`, `version` and the payload Schema, with an
optional complete `defaultPolicy`. Handler implementations are installed separately
through `handlerLayer(execute, decodePayload)`. Keeping provider code outside the
definition lets producers share contracts without importing worker dependencies.

### Why a handler registry?

Each definition installs its decoder and handler in `JobRegistry` through an
Effect Layer. Duplicate catalog registrations fail during installation; Schema
and handler services remain explicit Layer requirements. Applications assemble
the handlers their worker needs. This is not a compile-time proof that every
persisted catalog identity has a handler.

Catalog identity is **`(queue, name, version)`**. A registry is not a Kafka consumer
group or BullMQ Pro Group: it adds no independent subscription, execution ordering
or tenant fairness.

### Why producer slots, not just a job ID?

An order can produce a confirmation and an invoice. Each consequence needs its own
stable identity: **`(operation, operationId, slot)`**, within one jobs storage.
Using only the request ID would collapse them; inventing unrelated job IDs on each
request retry would duplicate them. Two slots may also produce the same job name.
Slots describe consequences, not concurrency permits or workflow dependencies.

```ts
const MailQueue = Queue.make("mail")
const PriorityMailQueue = Queue.make("mail.priority")
const Confirmation = Job.make({
  name: "order.confirmation",
  queue: MailQueue,
  payload: Schema.Struct({ orderId: Schema.String }),
  defaultPolicy: Policy.defaultPolicy
})

const PlaceOrder = Producer.make({
  operation: "orders.place",
  slots: { confirmation: Confirmation }
})
const request = {
  operationId: "place-041",
  payload: { orderId: "041" }
} as const
```

### Why bind the queue and allow a policy override?

They solve different problems:

| Setting         | Job definition                                        | Enqueue                                                          |
| --------------- | ----------------------------------------------------- | ---------------------------------------------------------------- |
| `queue`         | One fixed destination, part of catalog identity       | No queue override                                                |
| `defaultPolicy` | Optional complete policy                              | Policy required unless a complete default is definitely provided |
| `policy`        | Resolved with `Policy.make` or `Policy.defaultPolicy` | A complete replacement, never a partial merge                    |

An unrestricted queue override could send work somewhere no intended worker drains.
Choose a different job definition and bind it explicitly when another queue is
needed. A changed queue is a changed catalog identity, not a duplicate configuration
override. This priority definition deliberately has no default policy:

```ts
const PriorityConfirmation = Job.make({
  name: "order.confirmation",
  queue: PriorityMailQueue,
  payload: Schema.Struct({ orderId: Schema.String })
})
const RoutedOrder = Producer.make({
  operation: "orders.place-priority",
  slots: { confirmation: PriorityConfirmation }
})
const priorityPolicy = Policy.make({
  retryDelay: Duration.seconds(2),
  maxAttempts: 4
})

yield* RoutedOrder.enqueue("confirmation", {
  ...request,
  policy: priorityPolicy
})
```

The default belongs to the definition; an override belongs to this production.
Neither policy nor availability changes an existing matching job. The two
operations above intentionally have different producer identities.

## Production and identity

### Why require a transaction for `enqueue`?

Saving an order and publishing work in separate commits leaves a crash window.
`enqueue` joins the active transaction of the **configured client**; it never
silently opens another connection. The same database URL is not enough.

`jobs` below is the configured PostgreSQL integration. `saveOrder` is application
work using that same client and active transaction—not an independently run Promise.

```ts
// Avoid: the order may commit, then enqueue may fail.
yield* jobs.withTransaction(() => saveOrder)
yield* Confirmation.enqueueStandalone({
  ...request,
  producer: PlaceOrder.identity({ operationId: request.operationId, slot: "confirmation" })
})
```

```ts
// Together: commit both database writes, or roll back both.
yield* jobs.withTransaction(() =>
  Effect.gen(function* () {
    yield* saveOrder
    return yield* PlaceOrder.enqueue("confirmation", request)
  })
)
```

`enqueueStandalone` is for work with no accompanying business write. It owns its
transaction and rejects an active one from the configured client, rather than
committing a consequence inside a parent that could later roll back.
`enqueueInTransaction` retains an explicit capability path for qualified adapters.

### Why conflict instead of ignoring or replacing duplicates?

The producer tuple locates the consequence; queue, name, version and canonical payload
semantics establish whether it is **the same** consequence. A matching retry returns
`AlreadyPresent` with the first library-assigned `jobId`.

```ts
yield* PlaceOrder.enqueue("confirmation", request)
// Same identity, different content: JobIntegrityConflict, not an update.
yield* PlaceOrder.enqueue("confirmation", { ...request, payload: { orderId: "042" } })
```

Silently ignoring the second call could report success for work never scheduled;
latest-wins could change what an earlier accepted request meant. Debounce and
throttle are useful for coalescing updates, but are a different contract.
An integrity conflict must abort the business transaction; the PostgreSQL adapter
prevents a caught conflict from committing partial domain writes.

Policy and availability are excluded from semantic equality: a matching
duplicate keeps its **first configuration and artifact bytes**. Otherwise a
deployment-default change could turn a harmless request retry into a conflict or
move existing work. Re-enqueue is not a rescheduling API.

### Why not promise exactly-once?

Atomic enqueue protects database writes, not an external email or payment.
A worker can complete the external call and disappear before recording success.
Use a stable provider idempotency key, such as `context.jobId`, with stable content
and within the provider's retention window, or reconcile through the domain.

`Inserted` and `AlreadyPresent` describe production, not execution. Joined results
remain provisional until the outer transaction acknowledges COMMIT. A lost COMMIT
response remains unknown; absence of an application receipt is not permission to replay.

## Execution and failures

### Why no `ack()`?

The worker owns finalization; the handler returns success or a `JobFailure`.
An exposed acknowledgement could precede the actual work or conflict with a later
failure. Success asks the worker to attempt fenced completion—it does not bypass
storage uncertainty. BullMQ and effect-mq's normal worker APIs also finalize from
the handler result; this is not unique to effect-jobs.

### Why four failure outcomes?

| Outcome          | Example                                          | What conflating it would lose                                                                                  |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `Retry`          | Provider confirms temporary rejection            | Marking it terminal drops recoverable work                                                                     |
| `Dead`           | Recipient is permanently invalid                 | Retrying wastes attempts without changing the answer                                                           |
| `Isolate`        | Invalid artifact or broken credentials/invariant | Treating it as an ordinary rejection hides an operational incident; finite Dead retention could erase evidence |
| `OutcomeUnknown` | Connection lost after submitting the send        | Assuming rejection can duplicate an already accepted effect                                                    |

`Dead` is an understood terminal result; `Isolate` is quarantine for investigation
and is never automatically purged. Isolating every business rejection instead
creates an unbounded investigation backlog.

Here `send` is an application provider adapter with typed, classified outcomes;
`Codes` contains validated `FailureCode.define(...)` identifiers.

```ts
// Avoid: a lost response or invalid recipient is not a temporary rejection.
const retryEverything = send.pipe(
  Effect.mapError(() => JobFailures.Retry({ code: Codes.ProviderBusy }))
)
```

```ts
const deliver = send.pipe(
  Effect.catchTags({
    ProviderBusy: () => Effect.fail(JobFailures.Retry({ code: Codes.ProviderBusy })),
    InvalidRecipient: () =>
      Effect.fail(JobFailures.Dead({ code: Codes.InvalidRecipient })),
    InvalidCredentials: () =>
      Effect.fail(JobFailures.Isolate({ code: Codes.InvalidCredentials })),
    ResponseLost: () =>
      Effect.fail(JobFailures.OutcomeUnknown({ code: Codes.ResponseLost }))
  })
)
```

Domain services keep their own errors; the handler adapter maps them using normal
Effect composition. Persist bounded diagnostic codes, not raw errors, provider
responses or private identifiers. This sacrifices stored error detail to keep
sensitive data out of job records and built-in telemetry.

### Why is unknown different from retry?

A timeout, defect or interruption does not prove that nothing happened.
`OutcomeUnknown` is an attempt outcome, **not a lifecycle state**: without confirmed
finalization, the job remains Active for bounded lease recovery. Recovery can invoke
the handler again; it does not solve external idempotency.

An unknown **storage write** needs a different response: reconcile the original
claim token or exact finalization request. Do not immediately rerun a successful
handler merely because its completion write lost a response.

`attemptsMade` counts confirmed Complete/Retry/Dead/Isolate transitions, not
all invocations. `context.attemptNumber` is `attemptsMade + 1` and may repeat after unknown outcomes; it is
not an idempotency key. A separate `maxStalledCount` bounds uncertain recovery.

### Why fixed leases instead of heartbeats?

A fixed lease needs no background renewal loop, fitting bounded invocations such
as workerd. Heartbeats are possible there too, but require a live invocation and
renewal scheduling. We choose bounded ownership instead: each attempt must fit a
finite timeout, leaving lease time for the storage response budget. BullMQ and
effect-mq normally renew locks to support long-running work.

Database time controls eligibility, expiry and durable transitions; worker clock
skew must not grant ownership. Fencing rejects stale lifecycle writes, not external
requests already sent. Forced shutdown therefore cannot release executing work as
if it were safely unexecuted; scoped polling first allows a finite shared grace period.

### Why persist retries instead of using `Effect.retry`?

A retry may be due after its invocation has ended, especially in runtimes such as
workerd. `Effect.retry` keeps its delay inside the invocation; that schedule
disappears if the process or isolate stops. `JobPolicy` describes durable fixed-delay retry
rules; the worker persists the next availability without exponential backoff or jitter, so another
invocation or worker can continue it. The host still owns wakeups; persistence does
not keep an invocation alive. Local retries remain useful when safe to repeat.

## Payload and ownership boundaries

### Why encode payloads and keep semantic projections?

Payloads must survive process and isolate boundaries. Schema's decoded domain type
need not be JSON: dates and bigints can have explicit encoded representations.
The standard codec validates bounded durable artifacts before dispatch and compares
canonical semantics, not object key order or mutable
lifecycle state. Plain `JSON.stringify` alone does not provide that contract.

Encrypted values add another problem: the same plaintext can produce different
ciphertexts. `JobPayload.encrypted` integrates an application codec with Schema;
semantic comparison uses its stable keyed fingerprint, not encryption randomness.
The application owns authenticated encryption, keys and their separate lifecycles.
`JobPayload.protected` only marks an already-protected representation—it does not
encrypt or authenticate anything.

### The shorter decisions

- **Explicit versions:** incompatible payload changes need a new job version and
  retained old handlers; a database migration does not update old payload contracts.
- **Ordinary Layers:** handler and Schema services stay visible in Effect requirements,
  not a second dependency container. Each invocation has its own Scope.
- **Separate execution and scheduling:** a bounded drain works without a permanent
  poller, letting the host choose polling or external wakeups. Per-queue concurrency
  belongs to the worker instance, shared across its drains—not every replica.
- **Logical queues:** names route work; they do not provide tenant authorization,
  infrastructure isolation, per-key ordering or automatic fan-out.
- **Read-only wake hints:** `JobSchedule` observations can immediately become stale;
  saturation makes a missing availability inconclusive. Keep a finite repair wakeup.
- **Explicit cleanup:** deleting identity evidence ends deduplication. Domain receipts
  or references may require an application-owned, coordinated cleanup adapter.
- **New-job redrive:** preserve the original record and lineage instead of resetting
  its budget or overwriting its payload. Active cancellation is not supported.
- **No result RPC:** handlers complete with `void`; business results belong in domain
  storage rather than an `execute()` / `awaitResult()` protocol.
- **No implicit infrastructure:** imports start no workers, migrations or cleanup.
  Applications own pools and migrations; platform-specific adapters stay outside
  portable contracts, so core imports require neither Node APIs nor PostgreSQL or Drizzle.
