A request has committed a report job. It will stay queued until your application
explicitly starts a worker. Importing a definition or constructing a worker Layer
starts no polling, database pool or migration.

## Give execution a lifetime

Build one application-owned graph: configured jobs storage, shared contract groups,
complete `JobGroup.handlers` handler Layers, then `JobWorker.layer(catalog,
{ queues: [{ queue, concurrency }] })`. Installation captures Schema decoding and
application services. Worker construction captures `JobStorage` and every catalog
group's handler service. Within one worker installation, reuse the same
`JobGroup` instance for handler registration and worker setup. Recreating a
group with the same name and jobs creates a different installation key.
Separate installations can create their own groups.

The catalog contains queue-independent name/version contracts. Unsupported
versions are excluded from claims rather than dispatched to another decoder.

| Need                       | Public operation                                     | Lifetime                                                     |
| -------------------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| Process a bounded slice    | `JobWorker.drain(queue, { maxJobs, recoveryLimit })` | Waits for its scoped executions before returning normally    |
| Keep consuming on Node/Bun | `JobPolling.layer([queue], options)`                 | Starts loops when built; the Layer scope owns their lifetime |

Keep the polling Layer built for the application's intended lifetime. Building it
inside a short request scope stops those loops when that scope closes. Scope
closure first allows the finite shared `shutdownGrace` grace; expiry interrupts
remaining work. This does not establish whether an external report
provider completed a request. See [recovery](/docs/execution/recovery).

## Choose groups for independent deployments

Groups determine which handlers a worker installs. Queues determine where that
worker claims jobs. Package, team, group and queue boundaries can differ. For
example, a billing package can define separate groups for email and PDF work so
the email worker installs every handler in its email group and needs no PDF
handler or renderer service.

If email and PDF were in one selected group, both handlers would be required,

## Run different catalogs on different queues

Choose the **group** by which handlers belong together, and the **queue** by
which jobs should compete for the same capacity. Application size is a useful
starting point; observed wait times and deployment boundaries decide when to split.

| Application               | Example                                                                                                                                                                      | Why this boundary?                                                                                                                                                                                                        |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Small service             | `billing` and `notifications` groups, one `default` queue and one polling worker.                                                                                            | A single deployment and similar latency needs. Split when long jobs start delaying short ones.                                                                                                                            |
| Growing SaaS              | Transactional mail on `mail.transactional`; report generation on `reports.standard` and `reports.express`.                                                                   | Mail must not wait behind rendering. A report producer with a selectable slot chooses a lane from the customer's entitlement on the server. Reserve capacity for each lane, including standard.                           |
| Multiple bounded contexts | Billing owns invoice contracts; Identity owns sign-in mail. They can share a delivery queue. Give bulk billing exports a separately deployed worker with its own CPU budget. | DDD determines who owns the contract. Latency, required services, failure isolation and independent rollout determine which jobs share workers. A queue name alone does not isolate tenants or reserve provider capacity. |

Measure due-to-start latency per lane and the oldest waiting standard job. An
express lane can shorten waiting time; it cannot interrupt a running report or
speed up a saturated provider. Matching re-enqueue after a subscription upgrade
keeps the first queue. A queue per paying customer is rarely a useful default.

A worker supports every group in its catalog on every configured queue. For
queue-specific coverage, create separate worker instances in the same
application. This Effect uses the configured `JobStorage`. Each handler Layer
installs the exact group used to build its catalog.

```ts
const run = Effect.gen(function* () {
  const billingApi = yield* JobApi.make("billing").pipe(JobApi.addGroup(Billing))
  const reportingApi = yield* JobApi.make("reporting").pipe(JobApi.addGroup(Reports))
  const billing = yield* JobWorker.make(billingApi, {
    queues: [{ queue: FastQueue, concurrency: 4 }]
  })
  const reporting = yield* JobWorker.make(reportingApi, {
    queues: [{ queue: SlowQueue, concurrency: 1 }]
  })
  yield* serveWakeRequests({
    billing: billing.drain(FastQueue),
    reports: reporting.drain(SlowQueue)
  })
}).pipe(Effect.provide(Layer.mergeAll(BillingHandlers, ReportHandlers)))
```

Here `serveWakeRequests` is your application code. Run the corresponding bound
drain for each wake. Providing both handler Layers around the whole Effect keeps
their scoped dependencies alive while it serves wakes. Both `JobWorker.layer`
values would provide the same service key, so merging them cannot combine the
instances. The two instances above have independent limits of four billing
jobs and one report.

## Retire an old queue

A producer route change applies to new jobs. A matching replay returns
`AlreadyPresent` with the original job ID and leaves that job in its first queue.
An immediate wake sent to the producer's new route cannot wake work left on the
old route.

1. Start the new consumers and their fallback wakeups before switching producers.
2. Route new jobs to the new queue and keep the old consumers and wakeups running.
3. Retire the old consumers and wakeups after old producers can no longer refill
   the queue and no jobs there still need processing. Include delayed,
   retry-scheduled and active jobs that could still require recovery.

An empty drain only observes that no eligible job was claimed in that drain.
It does not show that the old queue has drained permanently.

## Read the limits correctly

Set `idlePoll` to a positive whole-millisecond `Duration`. The default is one
second before jitter. `shutdownGrace` defaults to 30 seconds and accepts
durations from zero through five minutes. `recoveryRetryInterval` accepts a
positive, bounded whole-millisecond `Duration` and defaults to
`Duration.seconds(30)`. Once that interval has elapsed during claim backoff, the
next eligible polling round attempts bounded recovery.

| Setting                   | Bound                                         | Meaning                                                                                 |
| ------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------- |
| `concurrency`             | Integer 1–64                                  | Per-queue permits shared by concurrent drains of the same worker; acquired before claim |
| `maxJobs`                 | Integer 1–10,000                              | Maximum started claims in one finite drain                                              |
| `recoveryLimit`           | Integer 1–10,000                              | Recovery budget per drain; storage requests are split into batches of at most 500       |
| `operationResponseBudget` | Positive bounded whole-millisecond `Duration` | Configured once on storage; workers consume that same budget                            |

Local concurrency is **per worker instance**, not a fleet-wide limit. Two separate
worker instances each have their own permits. Reusing a queue on one worker with
a different concurrency value fails configuration. Worker configuration rejects duplicate logical queues. Recovery is restricted to
the queue being drained; concurrent drains share that queue's fixed permits.

A stored lease must leave enough time for the attempt timeout **plus** the
operation response budget. Configure finite database acquisition, control and
release timeouts at the application adapter too.

## Interpret a drain result

| Result     | What was observed                                              | What to do next                                                                   |
| ---------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `Idle`     | An empty claim was observed                                    | Sleep before checking again; future jobs or concurrent production can still exist |
| `MoreWork` | The started-claim limit was reached                            | Schedule another bounded drain; it may find no work                               |
| `Backoff`  | Recovery, claim or reconciliation failed or remained uncertain | Delay; inspect its `phase` and supported telemetry                                |

`claimed` counts started claims, not successful reports. `recovered` counts
recovery transitions, not completions. A drain can return `MoreWork` even when a
handler's outcome remains unknown.

The polling implementation handles these results: idle polling defaults to
1,000 ms, backoff uses bounded steps from 1 to 30 seconds, and both sleeps add
jitter. `MoreWork` yields before continuing. Polling backoff controls store
pressure; [persisted retry policy](/docs/execution/retries) controls a job's next
eligible attempt.
