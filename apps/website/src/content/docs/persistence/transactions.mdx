<p className="ej-lead">Save the order. Schedule the work. Commit both together.</p>

A customer places an order. If the order is saved but the process stops before
enqueueing, its confirmation is lost. Put the application write and job enqueue in
**one PostgreSQL transaction**, so they share the same durable outcome.

<TransactionFlow />

## Write the request and enqueue

Use Drizzle for application queries and **`PgClient.withTransaction`** for the
transaction boundary. `PlaceOrder.enqueue` joins the active transaction of
that exact client. No second connection, savepoint or inner commit is created by the join.

`placeOrder` validates external input and creates a new order. Its unique
`operationId` rejects duplicates and rolls back the whole transaction, even when
the submitted fields match. The unique order ID also prevents a different
operation from claiming the same order. No additional job or order is created.
This path does not implement idempotent submission replay.

For that separate application contract, `placeOrderIdempotent` checks every
retained business field and invoice choice, then reuses the first job and receipt.
A changed SKU or quantity raises `OrderConflict`, even when the queued payload
matches. A changed job catalog or semantic payload under the same producer tuple
raises `JobIntegrityConflict`. Let these errors fail the transaction.

## Set up once, then serve requests

The application owns **one scoped PgClient**, its pool, finite acquisition/control/release
timeouts and migrations. Build `ApplicationLayer` once with that client; keep the same
PgClient service available to request handlers. Drizzle and the jobs adapter then
observe the same client's transaction service in the same Effect Context.

Apply `migrationSql` from `packages/database/src/Migrations.ts` through your host

This path is scoped to Effect 4.0.5, `@effect/sql-pg` 4.0.5 and the two
[qualified Drizzle snapshots](/docs/persistence/drizzle). `db.transaction` is excluded
from this supported route. No per-request pool or backend construction is needed.

## Acknowledge only what you know

An enqueue result **inside** the callback is provisional. A later write can still
fail. Return success only after the outer transaction acknowledges COMMIT.
Keep typed errors, defects and interruption visible to the transaction owner;
never catch an integrity conflict to commit the other writes.

The advanced use case's receipt records the exact operation-to-job mapping. The immutable order row
and unique business identity make matching acknowledged submission replay safe;
this is still not a complete HTTP response replay protocol. **Receipt absence never authorizes replay of an uncertain
mutation.** The application owns reconciliation. The queue does not rerun your
business callback to discover whether it committed.

## Commit a dependent handoff

The [order tutorial](/docs/start/tutorial) adds invoice creation beside confirmation.
Those order slots are independent. Invoice delivery is different: it needs a
persisted invoice, so the invoice handler explicitly produces the delivery job.

<CodeExample
  sourcePath="orders/apps/worker/src/orders/jobs/CreateInvoice.ts"
  region="handoff"
  role="Consumer + producer"
/>

One synthetic invoice per order makes the order ID a stable `invoice.create`
operation identity. The unique invoice/order reference and delivery tuple survive
retries. Invoice persistence and delivery enqueue share one transaction; a failed
invoice write rolls back the new job. No external provider call belongs inside
this transaction. A real invoice service needs its own idempotency/reconciliation
contract. This is application orchestration, not a built-in DAG or slot ordering.

## When the job is the whole transaction

Use `SendOrderConfirmation.enqueueStandalone(input)` for independent production with no
application write that must commit beside it. It owns a bounded transaction and
resolves after acknowledged commit. It rejects an active transaction of its
configured client.

Keep every transactional Effect awaited inside the owner callback. Do not call
`Effect.runPromise` inside it, fork unawaited work, retain transaction Context past
its lifetime, or independently commit a consequence of a parent transaction.
Workers can run handlers again after uncertain outcomes: make external effects
idempotent or reconcile them. This is not an exactly-once execution promise.
