Keep Drizzle for typed order queries and migrations while the queue joins the
same native PostgreSQL transaction. Schema declarations alone do not bind a
transaction: wire the runtime client explicitly.

## Choose one client before opening a transaction

For the bundled driver, use `DrizzlePostgresClient` and `makeWithDefaults` from
`drizzle-orm/postgres/effect`. Provide its scoped client to both Drizzle and
`PostgreSqlNative`. This is the route used by the Cloudflare Alchemy example;
it does not require `pg` or `@effect/sql-pg`.

The playground uses `@effect/sql-pg` instead: on rc.6 an interrupted query can
still be running on PostgreSQL when the invocation ends, and the bundled client
has not passed the playground's WebSocket Durable Object hibernation test.
Never retry a transaction on the other driver after a failure.

## Build the order tutorial with PgClient

1. The application provides its scoped `PgClient` from `@effect/sql-pg/PgClient`.
2. `drizzle-orm/effect-postgres.makeWithDefaults()` obtains that service for order
   and receipt queries.
3. Pass that exact client to `PostgreSqlNative.layer({ client,
operationTimeout })`, then provide the resulting `PostgreSqlApplication`
   to `PostgreSqlJobs.layerNoDeps({ ...mapping,
operationResponseBudget })`.
4. Supply the jobs Layer's `JobEnqueue` to the mutation. Run Drizzle queries and
   `PlaceOrder.enqueue({ slot: "send-confirmation", operationId, payload: { orderId } })` inside public `client.withTransaction(body)`.

The shared order example builds the Drizzle `Database` service and jobs producer
once from that same client. Application writes use Drizzle query builders.

Reuse the same configured client Layer reference. Separately building a client
with equal options does not establish transaction identity. Joining jobs adds
no BEGIN, savepoint, independent COMMIT or replay. The application retains pool,
migration, timeout and outer error/reconciliation ownership.

The supported transaction owner is `client.withTransaction` with Drizzle queries
in the same Effect context. Separately, the bundled `drizzle-orm/postgres/effect`
driver at Drizzle `1.0.0-rc.6` and Effect `4.1.3` passed a local qualification
of the ordinary `db.transaction` callback on Node, Bun and workerd: with one
scoped client, the domain row, job, payload and receipt shared a PostgreSQL
connection and transaction. The type probes check the inferred error and service
channels. This evidence does not extend to nesting, isolation options or other
drivers. See the disconnected rollback limitation below.

## Optional declarations for migrations

`makeJobTables` from `effect-jobs/PostgreSqlDrizzleSchema` returns
`{ mapping, jobs, payloads }`. It accepts `schema`, `jobsTable`, `payloadsTable`
and optional `extraIndexes(jobs)` for additive Drizzle indexes. Feed its `mapping`
to storage; keep the required fixed columns, constraints and indexes.
The application owns unique schema-wide names for its extra indexes.

A Drizzle select exposes the stored policy JSON with `maxAttempts`. Decode
`row.policy` with `Schema.decodeUnknownEffect(PersistedJobPolicy)` from
`effect-jobs/JobPolicy` to read the domain field `maxFinalizedAttempts`.

Generate and apply migrations with your application tooling. The SQL helper
`PostgreSqlSchema.migration(mapping)` generates only the library baseline; it does
not include `extraIndexes`. Neither declarations nor the runtime execute DDL.

Drizzle is optional: core imports and the PostgreSQL runtime do not import it.
A non-Drizzle application can use the SQL migration helper and a qualified
application adapter. The root `effect-jobs` export is empty; import focused public
subpaths rather than internal modules.

## Exact supported graph and limits

The current local candidate targets Effect **4.1.3**, optional native
**`@effect/sql-pg@4.1.3`**, and exactly Drizzle **`1.0.0-rc.6`**. The PgClient
native matrix uses Node **24.15.0**, Bun **1.4.2**, PostgreSQL **16.15** and pg
**8.23.0**. Use ordinary peer resolution, one physical Effect instance and the
intended native peers, without force installs or dependency overrides. This
qualification uses the exact local candidate tarball, not the registry release.

Own-source strict/exact-optional contracts (A+B) use the accepted dependency
`skipLibCheck: true` setting, with actual negative compiler checks. Full foreign
declaration checking (C, `skipLibCheck: false`) remains **known upstream FAIL**:
the native consumer reports three missing builder names in Drizzle's PostgreSQL,
MySQL and SQLite declarations. The UI consumer's Redux diagnostics are separate.

Real PostgreSQL qualification covers same-connection atomic writes, rollback,
concurrent duplicates/conflicts, interruption and synthetic lost response after
durable COMMIT. It does not qualify arbitrary drivers or versions, nested/options
semantics, real network/server crashes or production use. On rc.6 the bundled
driver can also return only the application error when a disconnected session's
`ROLLBACK` fails. That error is not an acknowledgement of rollback.

Return to [transaction ownership](/docs/persistence/transactions/) before adapting
this graph to application requests.
