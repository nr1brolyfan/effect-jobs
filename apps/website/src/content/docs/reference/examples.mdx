The [Getting Started guide](/docs) builds an order application.
The API produces work, the worker processes it, and both share job contracts.
Find the complete example in `apps/website/examples/docs/orders`.

## Share a payload schema with another module

When a module needs to validate a payload independently, export the named Schema
directly and reuse it in the lazy job declaration. Keep concrete database,
mailer, worker and key-provider wiring in the applications that use them.

[its setup](/docs/execution/workers/#choose-groups-for-independent-deployments).
Local setup can keep its schema inline when it has no independent consumers.
If multiple modules in one worker installation need the same resolved group
instance, share it through a small domain Layer. The schema import works on
its own.

These are application example paths, not new library exports or a mandatory
microservice layout. The API imports shared contracts, not worker/provider code.
Each role composes its own startup with the shared `PersistenceLayer`.

`(operation, operationId, slot)` locates retained job evidence. Matching job name,
version, payload format and semantic payload return the original ID. Changes to
those fields conflict. Queue, policy and initial availability remain first-write-wins. Removing all evidence ends that deduplication
window. Whole-operation safety additionally needs the unique order and receipt.

## Compose and run

Copy the [Orders example](https://github.com/nr1brolyfan/effect-jobs/tree/main/apps/website/examples/docs/orders) and run this from the copied directory:

```sh
bun add --exact effect-jobs
```

Apply the exported migration SQL with your migration tool **before startup**.
This DDL reuses the library jobs schema; it is not a copied second jobs schema.
Set `DATABASE_URL` privately. The application owns its pool and finite native
acquisition/control/release deadlines. Server-side statement and lock deadlines
bound healthy-server work, not every network failure.

<CodeExample sourcePath="orders/apps/worker/src/main.ts" role="Composition" />

The included `package.json` defines the `#orders`, `#database`, `#api/orders`
and `#worker/orders` import aliases. The `development` condition resolves
TypeScript sources; compiled Node and Bun programs use `dist` instead.
From the copied source root, run the introductory confirmation:

```sh
OPERATION_ID=submission-1 ORDER_ID=order-1 bun --conditions=development apps/api/src/main.ts
WORKER_MODE=confirmation bun --conditions=development apps/worker/src/main.ts
```

Then use a **new** submission for the expanded application:

```sh
WITH_INVOICE=true OPERATION_ID=submission-2 ORDER_ID=order-2 bun --conditions=development apps/api/src/main.ts
WORKER_MODE=drain bun --conditions=development apps/worker/src/main.ts
WORKER_MODE=drain bun --conditions=development apps/worker/src/main.ts
WORKER_MODE=poll bun --conditions=development apps/worker/src/main.ts
```

Choose finite drains or continuous polling. A later drain may be needed if a new
handoff was not visible before an empty claim. Inspect durable invoices and mail
records rather than treating claim counts as proof of completion. For Node, run `bun run build` with the included standalone `tsconfig.json`, then
invoke `node dist/apps/api/src/main.js` or `node dist/apps/worker/src/main.js`
with the same environment settings.

The example records mail locally and does not contact an email provider.
