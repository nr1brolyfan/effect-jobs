These docs cover the local, unpublished `effect-jobs@0.1.0-alpha.3` candidate
and its qualified Effect `4.1.3` peer. The historical npm release
`effect-jobs@0.1.0-alpha.2` used Effect `4.0.5`.

From the candidate checkout, build and pack the library with `bun run build`
and `npm pack --ignore-scripts`. Install that tarball from your application directory:

```sh
npm install --save-exact /path/to/effect-jobs-0.1.0-alpha.3.tgz effect@4.1.3
```

Keep these versions exact in the application manifest so subsequent installs do
not widen the qualified Effect/SQL peer graph. No force install, peer override
or dependency patch is part of this setup.

## Choose the database integration

For PostgreSQL with Drizzle's bundled client (`drizzle-orm/postgres/effect`), install:

```sh
npm install --save-exact drizzle-orm@1.0.0-rc.6
```

The order tutorial and the playground instead use `PgClient` with
`drizzle-orm/effect-postgres`. For that route, also install:

```sh
npm install --save-exact @effect/sql-pg@4.1.3 pg@8.23.0
```

The exact qualified Drizzle peer is `1.0.0-rc.6`, not an arbitrary release
range. Use public
`client.withTransaction` with queries in the same Effect context; see
[native Drizzle integration](/docs/persistence/drizzle).

| Component                    | Supported qualification scope                                                                                         |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Effect and native SQL client | Exact `4.1.3`                                                                                                         |
| Node.js                      | `24.15.0` qualification; package engine `>=24.15.0 <25`                                                               |
| Bun                          | `1.4.2` qualification                                                                                                 |
| Persistence                  | PostgreSQL with application-owned pools and migrations                                                                |
| Declaration checks           | Own strict/exact-optional source checks; separately recorded upstream Drizzle declaration failures remain unresolved. |

Other runtimes, driver versions and production deployment are not established by
these examples. The queue's portable core does not imply a qualified storage on
every platform.

## Import focused modules

Use subpaths such as `effect-jobs/Job`, `effect-jobs/JobQueue` and
`effect-jobs/JobPolicy`. The root export is empty. Core imports require no
PostgreSQL or Drizzle peer, and imports do not connect to a database or start a
worker.

Create and migrate the jobs tables before running a worker. Backend readiness
checks validate the expected schema; they do not run migrations. Follow
[PostgreSQL setup](/docs/persistence/postgresql) for storage, then
[run your first job](/docs/start/first-job).
