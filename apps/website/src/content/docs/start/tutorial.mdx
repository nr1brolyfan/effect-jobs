Let's start with a small example that shows why background jobs are useful.
A customer places an order: we save it to the database, then send a confirmation
email. This is a reasonable starting point, but it has a few problems.

Here, `Database` is our application's Drizzle service and `TransactionalEmails`
sends customer emails through our chosen provider. This `placeOrder` use case
lives in the API's `orders` feature module. The request has already been validated
and authorized.

<CodeExample
  sourcePath="orders/apps/api/src/orders/Orders.ts"
  region="request"
  role="Producer without effect-jobs"
/>

1. ## Dual-write problem

   Saving the order and sending its confirmation are two separate actions,
   not one atomic operation. If our application crashes between them, or the
   email provider rejects the send, the order is already saved but the customer
   may not receive a confirmation. This gap is the **dual-write problem**.

2. ## A slow provider means a long loading screen

   Even a healthy provider can be slow. Because our request waits for email,
   the customer can be stuck on a loading screen for many seconds—even though
   their order is already saved. That is unnecessary waiting and a poor checkout
   experience. A provider failure does not mean the order failed.

3. ## The confirmation email does not need to arrive immediately

   The customer needs to know their order was accepted straight away. The email
   is important, but it does not need to arrive at that exact moment: a small
   delay is acceptable. We can respond first and send it as durable background
   work. A detached in-process task is not enough—it disappears when the process stops.

With effect-jobs, commit the order and its durable send-email job in **one
PostgreSQL transaction on the same client**. Respond after the acknowledged
commit without waiting for email; a worker makes the external call separately.
This makes the database writes atomic, not the database and external email.
Delivery is not exactly-once: external idempotency and uncertain outcomes still matter.

For local runs, the mail adapter records messages in PostgreSQL instead of
sending real emails. You do not need a provider account or credentials.

## 2. Handle the job in the worker

With the request finished, a worker can pick up the confirmation. Its handler
receives a decoded `payload` and `context`. Here the payload contains
only the order ID, and `context.jobId` supplies a stable delivery key across
handler retries. The application mail service owns delivery and its error contract.

<CodeExample
  sourcePath="orders/apps/worker/src/orders/jobs/SendConfirmation.ts"
  region="handler"
  role="Consumer"
/>

`EmailBusy` means a known replay-safe rejection and becomes `Retry`.
`EmailUncertain` means acceptance cannot be established and becomes `OutcomeUnknown`.
A real provider may have sent email before a timeout: queue deduplication cannot
prove exactly-once delivery. Its adapter needs idempotency or reconciliation.
Defects and interruption remain distinct from these typed outcomes.

To make it run, install the handler Layer and the registry,
then explicitly run a bounded drain with the same application services. The API
imports only shared contracts and database code; it never imports this handler or
a mail adapter. API and worker are roles that can also share one host process.

<CodeExample
  sourcePath="orders/apps/worker/src/main.ts"
  region="confirmation-composition"
  role="Composition"
/>

A drain waits for its bounded executions, not all future retries. Its counts
measure claims, so inspect the durable business result when verifying completion.
The runnable local adapter inserts one `synthetic_mail` row per delivery key;
that is a synthetic adapter property, not a production provider guarantee.

## 4. Send the invoice only after it exists

We cannot send an invoice before it exists. This calls for a **dependent handoff**,
so the invoice handler explicitly produces a new job. It is not a third independent
slot of `order.place`, and the worker does not wait for all earlier slots.

<CodeExample
  sourcePath="orders/apps/worker/src/orders/jobs/CreateInvoice.ts"
  region="handoff"
  role="Consumer + producer"
/>

This example has exactly one synthetic invoice per order, enforced by the unique
order reference. The invoice ID and the `invoice.create` operation ID therefore
both use the order ID. Unlike the original submission identity, this key denotes
the one immutable invoice result; it stays the same across handler retries.
A fresh UUID per attempt would create a fresh delivery consequence.

The invoice row and delivery job commit together. The delivery worker cannot
observe the job before its invoice commits. Repeating the handoff finds the same
invoice and job; a failed invoice write rolls back the new delivery job as well.
No mail or non-idempotent provider request runs inside this SQL transaction.
A real PDF or invoice provider would need its own repeatable result and
reconciliation contract before this boundary.

<CodeExample
  sourcePath="orders/apps/worker/src/orders/jobs/SendInvoice.ts"
  region="handler"
  role="Consumer"
/>

The delivery handler reads the committed document and calls the same application
mail service with its stable job ID. Bounded lease recovery may invoke it again;
the external service still owns idempotency and reconciliation. There is no built-in
DAG, join, parent-child status or exactly-once email guarantee.

so they have different producer operations, while keeping the same handler/name.
The compact recipe is an additional contract; the introductory invoice-ID-only

## 5. What if something fails?

If the order transaction rolls back, none of its new order or jobs survive.
The advanced use cases also roll back their new receipts. For a lost response,
the beginner create path must not blindly resubmit or claim replay success; use
an application reconciliation path. The advanced example reads its exact receipt. A mail timeout may
follow acceptance; keep that outcome uncertain and reconcile the provider.

The small shared policy allows three finalized attempts with a fixed five-second
retry delay. Its other defaults are a 30-second attempt timeout, a 90-second lease,
one stalled recovery, 90-day Completed retention and infinite Dead retention.
`defaultPolicy` supplies that complete policy when enqueue omits one. A complete
override replaces the entire default; without a definitely provided default,
policy stays required. Optional/dynamic defaults are typed conservatively.

<CodeExample
  sourcePath="orders/apps/api/src/orders/InvoiceDelivery.ts"
  region="policy-override"
  role="Producer"
/>

Changing a definition default from three attempts to five affects new insertions
only. Matching duplicates keep their first policy and availability, including
after a deployment changes defaults. The worker executes stored configuration;
a default change alone needs no job version bump and changes no pending row. Attempt numbers can repeat after
uncertainty and are not idempotency keys. An attempt timeout does not prove that
an external action failed.

Keep expected typed failures, defects and interruption distinct. The invoice
handler conservatively maps SQL/control uncertainty to `OutcomeUnknown`;
it does not blindly retry the whole transaction. An absent receipt also does not
establish `NotCommitted`. See [transactions](/docs/persistence/transactions),
[retry safety](/docs/execution/retries), [fencing and recovery](/docs/execution/recovery)
and [retention](/docs/persistence/postgresql#plan-retention-with-receipts) for the operational boundaries.

```sh
# Or process continuously until the application closes its Scope:
WORKER_MODE=poll bun --conditions=development apps/worker/src/main.ts
```

Expect one order receipt with two job references, one synthetic invoice with its
delivery reference, and two synthetic mail records. Check those durable results,
rather than treating claim counts as proof of completion. The [complete source and
qualification commands](/docs/reference/examples) use the same paths and contracts.
