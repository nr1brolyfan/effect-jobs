# PostgreSQL attempt history

Attempt history is optional operational evidence of persisted worker finalizations and
lease-expiry recoveries. It has no completeness guarantee. It grants no authority
to reconcile, rerun or deliver work and serves no business audit purpose.

## Capture

Each PostgreSQL jobs instance defaults to `off`. `problems` captures finalizations
that result in RetryScheduled, Dead or Isolated and captures lease recoveries.
`all` also captures Completed finalizations. Workers sharing a store should use the
same setting. Each enabled mode requires an explicit positive safe integer TTL in
milliseconds. TTL changes apply to newly captured events.

Capture occurs inside the same owned, fenced transaction as the transition, using
its sampled database time. An insert failure aborts that transaction. An ambiguous
commit follows the existing Unknown protocol. Reconciliation reads the existing
lifecycle state and adds no history. Finalization records the actual resulting
state, including Dead when a Retry command exhausts its budget. Recovery records
the resulting stall count and is a distinct event even when it ends in Dead. The
fallback recovery quarantine writes no history when decoding or planning fails:
that path cannot establish a canonical post-transition version and stall count.
Claim-time isolation, release, enqueue and operator changes are outside capture.

Each event contains the job ID, post-transition lifecycle version, DB timestamp,
event kind, resulting state, the finalized-attempt number or stall count, and a
validated failure code when the transition supplies one. RetryScheduled carries
the persisted next eligibility time. Payloads, results, raw errors and lease
tokens stay outside history.

## Reads and retention

Read a bounded page for one job in descending lifecycle-version order. Pass the
opaque continuation to read older entries for that job. Each page hides entries
whose persisted expiry is at or before the sampled database time. Pages can
change as time passes and writers commit. Empty pages and gaps imply no
conclusion about job existence or execution.

Cleanup is separately invoked by the application, including after capture is
disabled. Each invocation deletes at most the requested bounded count of expired
history rows and only touches history. Parent deletion cascades immediately, so
history does not extend job retention or deduplication. The library creates no
maintenance timer.

## Schema and rollout

The application applies the additive migration or equivalent qualified Drizzle
declaration. The migration creates a separate relation with a per-job version key,
a cascading foreign key and an expiry index. It performs no backfill or job
rewrite. Default construction and readiness work without that relation.

With capture enabled, readiness checks the history table's column types,
nullability and generated definitions, its per-job version key, cascading
foreign key and expiry index in the PostgreSQL catalog. The writer supplies values
for every history column, so `GENERATED ALWAYS AS IDENTITY` is incompatible.
`GENERATED BY DEFAULT AS IDENTITY` accepts the explicit values, including the
version assigned by the lifecycle transition.

This structural check does not exercise writes or evaluate application rules.
Custom DDL, including constraints and triggers, must allow all supported history
events and their values, including lease recoveries and their resulting states.
The application owns database privileges for capture and maintenance.

Apply the migration, replace existing workers, then enable capture. Older writers
and disabled periods leave gaps. Rolling back the binaries preserves existing
history subject to stored expiry and parent cleanup. The upgrade fixture establishes
compatibility with the pinned pre-feature schema and writer.

### Application setup

Use the same table mapping for migration generation and runtime. Run the SQL
below in your migration transaction after the base jobs and payload tables exist.

```ts
import * as PostgreSqlSchema from "effect-jobs/PostgreSqlSchema"

const mapping = PostgreSqlSchema.tables({ schema: "billing", jobsTable: "tasks" })
const migrationSql = PostgreSqlSchema.attemptHistoryMigration(mapping)
```

With Drizzle, export the optional declaration alongside the original table
objects and generate the additive migration with the app's migration tool.

```ts
import * as PostgreSqlDrizzleSchema from "effect-jobs/PostgreSqlDrizzleSchema"

const storage = PostgreSqlDrizzleSchema.makeJobTables({
  schema: "billing",
  jobsTable: "tasks"
})
export const { jobs, payloads } = storage
export const attemptHistory = PostgreSqlDrizzleSchema.makeAttemptHistoryTable(storage)
```

Apply the migration first. Roll out the new binaries with capture omitted or
`{ mode: "off" }`. Once all workers for this store run the new version, choose
one mode and TTL for that store and run `jobs.ready` before starting workers.

```ts
import { Duration } from "effect"
import * as PostgreSqlJobs from "effect-jobs/PostgreSqlJobs"

const setup = PostgreSqlJobs.make({
  schema: "billing",
  jobsTable: "tasks",
  operationResponseBudget: Duration.millis(100),
  attemptHistory: { mode: "problems", ttlMillis: 7 * 24 * 60 * 60 * 1000 }
})
// Use mode "all" to also capture completions.
```

Given your configured service, read the first page and pass its cursor as
`before` in the same job's next request. Schedule cleanup from your application
and use a bounded batch per invocation. Reads and cleanup require the optional
migration even when capture is off.

```ts
import type { JobId } from "effect-jobs/JobId"
import type { AttemptHistoryCursor, Service } from "effect-jobs/PostgreSqlJobs"

const readPage = (jobs: Service, jobId: JobId, cursor?: AttemptHistoryCursor) =>
  jobs.attemptHistory.read({
    jobId,
    limit: 50,
    ...(cursor === undefined ? {} : { before: cursor })
  })

const cleanExpiredHistory = (jobs: Service) => jobs.attemptHistory.cleanup(100)
```

To roll back, disable capture before replacing binaries and retain the additive
schema. Use an upgraded maintenance process with capture off to continue TTL
cleanup if required during the rollback.

### Upgrade fixture

The PostgreSQL runtime matrix uses
`tests/postgresql/fixtures/BeforeAttemptHistory.sql` as a frozen schema from
`ff593dcb9c0533be955e62711d8f724c3fb7910b`. For an old-binary upgrade check,
build that revision with the pinned tools and set
`D6_ATTEMPT_HISTORY_BASELINE_MODULE` to the absolute path to its compiled
`dist/postgresql/PostgreSqlJobs.js` before running
`bun run test:postgresql:matrix all`. The same fixture exercises that binary
before and after the migration, including legacy parent cleanup.
